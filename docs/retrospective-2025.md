# 2025년 첫 해커톤 회고 — 약장수

> **작성 관점:** 2026년에 돌아본 개인 기록. 당시의 코드와 영상으로 확인된 사실, 제가 기억하는 경험, 지금의 해석을 구분해 남깁니다.

## 시작: 무엇을 어떻게 해야 할지도 몰랐던 세 명

2025년 가을, 처음 해커톤에 참여했습니다. 팀은 세 명이었습니다. 각자 어떤 일을 맡아야 하는지, 어떻게 코드를 나누고 결과물을 합칠지조차 명확하게 정리하지 못했습니다. 저도 웹 서비스를 구현하는 지식과 경험이 충분하지 않았습니다.

그나마 제가 시도할 수 있었던 방법은 **Cursor를 유료로 사용해 개발을 진행하는 것**이었습니다. 코드를 능숙하게 직접 설계하고 구현했다고 이야기할 수는 없지만, AI 코딩 도구의 도움을 받아 실제 화면을 만들고 동작을 확인해 보는 경험을 했습니다.

이 점은 부끄러워서 감추고 싶은 부분이 아닙니다. **도구의 도움을 받아 무언가를 처음 완성하려고 시도했던 시절**이라는 사실 자체가 기록할 가치가 있습니다.

## 우리가 만든 것: '약장수'

'약장수'는 약 이름·증상으로 목록을 검색하고, 증상을 입력하면 관련 의약품 정보를 답하는 챗봇 형태의 프로토타입입니다.

2025년 10월 말의 로컬 시연 영상에는 의약품 목록, 카테고리 필터, 채팅 화면을 오가며 테스트한 장면이 남아 있습니다. [현재 코드 기준 구현 상세](technical-review.md)는 별도 문서에 정리했습니다.

당시 코드를 살펴보면 처음부터 완성된 의료 시스템을 만든 것은 아닙니다. 추천의 핵심은 키워드에 반응하는 규칙 기반 로직이며, 의약품 데이터에도 정확성 문제가 있습니다. 당시에는 이 차이를 제대로 인식하거나 설명하지 못했습니다.

## 지금 돌아보니 보이는 것

### 그래도 남기고 싶은 성과

- 모르는 기술을 만나도 도구를 찾아 시도했고, 브라우저에서 확인할 수 있는 서비스 화면을 만들었습니다.
- 검색·필터링·채팅·API 응답 같은 웹 애플리케이션의 기본 흐름을 처음 접했습니다.
- 남겨둔 코드와 영상 덕분에 지금도 당시의 결과를 검토할 수 있습니다.

### 당시에는 부족했던 것

- **역할 분담과 협업:** 누가 무엇을 만들고 어떤 부분을 책임지는지 합의하지 못했습니다.
- **설계:** 요구사항, 데이터의 신뢰성, API와 화면의 경계를 먼저 정의하지 않았습니다.
- **정확성:** 그럴듯한 답변을 보여주는 것과 실제로 맞고 안전한 정보를 제공하는 것은 전혀 다른 문제입니다.
- **검증:** 테스트, 예외 처리, 보안, 기능의 실제 동작을 증명할 근거가 충분하지 않았습니다.
- **AI에 대한 이해:** Cursor로 개발한 프로젝트와 LLM을 실제로 호출해 판단하는 서비스는 다른 개념인데, 그 구분이 흐릿했습니다.

이 내용은 특정 팀원의 잘못을 따지는 기록이 아니라, **팀 전체가 개발을 낯설어하던 시기의 제 경험을 솔직하게 정리한 것**입니다. 당시 팀원별 정확한 코드 기여도는 현재 보유한 자료로 확인하기 어렵습니다.

## 1년 뒤: 2026년 EIDOS 해커톤과 달라진 점

2026년에는 5개 컴퓨터공학 관련 학술 동아리가 연합한 해커톤에서 [EIDOS](https://github.com/2026ENDPoinT/team19) 팀의 **백엔드(BE)** 개발을 담당했습니다. EIDOS는 강의 PDF를 학습 단계별 시각화 숏폼 강의 시리즈로 만드는 프로젝트입니다.

| 돌아보는 기준 | 2025 약장수 | 2026 EIDOS |
| --- | --- | --- |
| 저의 역할 | 팀원 중 Cursor를 활용해 구현을 시도 | BE 담당, API·저장·작업 실행 흐름 구현 |
| 개발 출발점 | 무엇을 만들고 나눌지 불명확 | AI·FE·BE 역할과 파트별 계약 정리 |
| 핵심 관심 | 우선 화면과 기능이 동작하도록 만들기 | 동작뿐 아니라 상태·실패·재시도·데이터 보존 고려 |
| 협업 | 도구 활용과 구현 자체가 익숙하지 않음 | GitHub 기반 결정·질문·제안·계약 문서 활용 |
| 검증 | 자동화된 검증 근거가 부족 | 테스트와 통합 시나리오, 오류 상황 검증을 개발 과정에 포함 |

2026년 경험이 있었다고 2025년의 부족함이 사라지는 것은 아닙니다. 오히려 약장수 소스를 다시 읽을 때, 그때는 보이지 않던 구조적·안전성 문제를 발견할 수 있게 되었다는 것이 변화입니다.

## 이 저장소를 남기는 이유

프로젝트를 지우거나 최신 기술로 덮어쓰기보다 **그때 만들었던 결과, 그때 몰랐던 것, 지금 새로 이해한 것**을 함께 남기는 편이 저의 성장 과정을 더 잘 보여준다고 생각합니다.

해커톤의 수상 여부, 주최 기관의 정식 명칭, 팀원별 작업 세부 내역은 현재 확보한 자료로 검증되지 않았으므로 기재하지 않았습니다. 추가 자료가 생기면 당시 기록과 구별해서 보완할 예정입니다.
